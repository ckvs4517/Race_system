# Spin League 功能修改規格：私下確認報名＋飲品選擇

> 本文件是提供給 AI／開發者使用的實作規格。  
> 請先閱讀專案根目錄的 `AGENTS.md`、`DEVELOPMENT.md`，再依本文件修改。  
> 本次重點是調整報名流程與新增飲品選擇，不處理金流。

---

## 1. 產品定位

Spin League 的核心定位是：

- 管理已確認參賽者
- 現場報到
- 產生賽程
- 記分
- 排名
- 公開顯示賽事進度

系統不負責：

- 線上付款
- 退款
- 對帳
- 付款審核
- 自動候補通知
- 公開售票
- 完整報名平台功能

付款與參賽資格仍由主辦人透過私訊處理。

---

## 2. 新的報名流程

### 2.1 預期流程

```text
參賽者私訊主辦人
→ 主辦人確認名額與付款
→ 主辦人傳送「參賽資料填寫連結」
→ 參賽者填寫選手資料與飲品
→ 系統直接加入正式參賽名單
→ 比賽當天現場報到
→ 產生賽程並開始比賽
```

### 2.2 重要原則

- 這個連結不是「公開報名連結」。
- 介面名稱應改為「參賽資料填寫連結」。
- 表單只提供給已完成參賽資格與付款確認的人。
- 送出後直接進入正式參賽名單。
- 不再需要主辦人於系統內進行第二次核准。
- 若名額已滿，表單必須拒絕送出。
- 主辦人仍可在後台修改或移除參賽者。

### 2.3 表單提示文案

資料填寫頁需清楚顯示：

> 本表單僅供已與主辦人完成參賽資格及付款確認者填寫。  
> 每位參賽者包含一杯飲品，請確認選擇後再送出。  
> 飲品送出後無法自行修改，如需更改，請於比賽前一天私訊主辦人。

---

## 3. 報名審核流程調整

### 3.1 移除或停用的概念

本次流程不再需要以下人工審核狀態：

- `pending`
- `approved`
- `rejected`
- 主辦人逐筆核准
- 主辦人逐筆拒絕
- 付款狀態
- 系統內候補審核流程

若現有程式仍使用報名申請資料表或狀態，不一定要立即刪除舊資料結構，但新的資料填寫流程不可再要求後台核准。

### 3.2 新提交的處理方式

提交資料後：

1. 驗證賽事存在。
2. 驗證填寫功能仍開放。
3. 驗證報名 Token。
4. 驗證必填欄位。
5. 檢查正式名單人數是否已達本場容量。
6. 檢查選手名稱及電話是否重複。
7. 驗證飲品選項是否合法。
8. 直接加入 `tournament.players`。
9. 建立該選手的 `participantStates`。
10. 建立該選手的 `participantDetails`。
11. 儲存至 D1。
12. 回傳成功畫面。

新參賽者狀態建議為：

```js
participantStates[playerName] = {
  status: 'active',
  checkedIn: false,
};
```

## 4. 飲品功能需求

### 4.1 飲品功能目的

咖啡廳主辦的比賽會附一杯飲品。系統需讓：

- 主辦人設定本場可選飲品。
- 參賽者填表時先選好飲品。
- 主辦人提前知道每種完整飲品要準備幾杯。
- 選手名單顯示每位選手選擇的飲品。
- 報到 Checklist 顯示每位選手選擇的飲品。
- 主辦人可在後台替選手修改飲品。

### 4.2 常規飲品

#### 咖啡類

咖啡先選風味，再選調製方式。

風味：

- 藍莓
- 椰子
- 哈密瓜

調製方式：

| 咖啡風味 | 美式 | 拿鐵 | 加可樂 |
|---|---:|---:|---:|
| 藍莓 | 可選 | 可選 | 不可選 |
| 椰子 | 可選 | 可選 | 可選 |
| 哈密瓜 | 可選 | 可選 | 不可選 |

完整顯示名稱範例：

- 藍莓咖啡／美式
- 藍莓咖啡／拿鐵
- 椰子咖啡／美式
- 椰子咖啡／拿鐵
- 椰子咖啡／加可樂
- 哈密瓜咖啡／美式
- 哈密瓜咖啡／拿鐵

#### 無咖啡因

固定品項：

- 汽水
- 果汁
- 青汁拿鐵

### 4.3 未來擴充

主辦人未來可能依活動情況：

- 新增咖啡風味
- 停用咖啡風味
- 新增調製方式
- 停用調製方式
- 新增無咖啡因飲品
- 停用無咖啡因飲品
- 修改顯示順序

因此不能把所有飲品寫死在 UI 中。

## 5. 飲品設定介面

### 5.1 建立／編輯賽事

在建立或編輯賽事頁增加「本場飲品設定」。

預設帶入常規菜單：

- 藍莓：美式、拿鐵
- 椰子：美式、拿鐵、加可樂
- 哈密瓜：美式、拿鐵
- 汽水
- 果汁
- 青汁拿鐵

主辦人可針對本場：

- 啟用或停用飲品功能
- 新增品項
- 修改名稱
- 停用品項
- 調整排序
- 修改提示文字

### 5.2 預設菜單與本場菜單

建議概念上區分：

- 咖啡廳常規預設菜單
- 本場賽事菜單

建立賽事時，將預設菜單複製到本場賽事中。

之後修改預設菜單時，不得自動改變舊賽事的飲品內容。

第一版若不做全域預設菜單管理，也可以先在建立賽事時自動產生常規預設值，但資料仍必須保存在單一賽事中。

## 6. 參賽者飲品選擇介面

### 6.1 表單互動

先選擇飲品類型：

```text
○ 咖啡
○ 無咖啡因
```

選擇咖啡後：

1. 選擇咖啡風味。
2. 再顯示該風味允許的調製方式。

選擇無咖啡因後：

- 直接選擇汽水、果汁或青汁拿鐵。

### 6.2 送出前確認

送出前需顯示確認資訊：

```text
選手 ID：88戰隊 小不點
飲品：椰子咖啡／加可樂
```

並顯示：

> 飲品送出後無法自行修改。  
> 如需更改，請於比賽前一天私訊主辦人。

### 6.3 必填規則

當本場飲品功能為啟用時：

- 飲品為必填。
- 咖啡類必須同時選擇風味和調製方式。
- 無咖啡因必須選擇一個有效品項。
- 前端及 Worker 後端都必須驗證。
- 不可只依賴前端限制。

當飲品功能為停用時：

- 不顯示飲品欄位。
- 允許沒有飲品資料的參賽者加入。

## 7. 後台選手名單

每位選手需顯示完整飲品名稱，例如：

```text
88戰隊 小不點
飲品：椰子咖啡／加可樂
狀態：尚未報到
```

後台必須支援：

- 修改選手名稱
- 修改聯絡資料
- 修改飲品
- 移除選手
- 手動新增選手時選擇飲品

若主辦人手動新增選手但尚未決定飲品，可暫存為：

```text
尚未選擇
```

後台應以明顯方式提示仍有選手尚未選飲品。

- 咖啡豆總量統計
- 奶類總量統計
- 可樂總量統計
- 原料分類統計
- 複雜圖表

## 9. 報到 Checklist

報到畫面需在選手名稱下方顯示完整飲品名稱：

```text
☐ 88戰隊 小不點
   椰子咖啡／加可樂

☐ Matthew
   青汁拿鐵
```

手機版應將飲品放在選手名稱下方，不建議新增過窄的表格欄位。

第一版不需要增加：

- 飲品已製作
- 飲品已領取
- 飲品製作進度

報到與飲品領取暫時不拆成兩套狀態。

## 10. CSV 匯出

現有選手／賽事 CSV 匯出需加入飲品欄位。

範例：

```csv

88戰隊 小不點,椰子咖啡／加可樂,已報到
Matthew,青汁拿鐵,尚未報到
```

舊賽事沒有飲品資料時，飲品欄位可留空。

## 12. 菜單修改規則

- 尚未被任何參賽者選擇的品項，可直接刪除。
- 已被選擇的品項不可直接刪除，只能停用。
- 停用後，新填表者看不到。
- 已選擇該品項的舊參賽者仍需正常顯示。
- 修改菜單顯示名稱時，不自動修改已提交選手的 `displayName`。
- 主辦人可手動修改單一選手的飲品。
- 賽程開始後，菜單預設鎖定。
- 如需在賽程開始後修改，應顯示警告並由主辦人主動確認。

## 13. 名額與重複資料保護

即使連結是私下分享，Worker 仍需保留基本防護。

### 13.1 名額限制

送出時檢查：

```text
tournament.players.length < registrationSettings.capacity
```

不得只檢查固定 32 人上限。

### 13.2 重複選手

至少檢查：

- 同一賽事內選手名稱不可完全相同。
- 同一賽事內正規化電話不可重複。

台灣電話正規化範例：

```text
0912-345-678
0912 345 678
0912345678
+886 912 345 678
```

以上應視為同一支電話：

```text
0912345678
```

### 13.3 Token 與關閉機制

主辦人需能：

- 開放參賽資料填寫。
- 複製參賽資料填寫連結。
- 關閉參賽資料填寫。
- 關閉時更換 Token，使舊網址失效。
- 開始報到或建立賽程時可自動關閉填寫。

## 14. 舊資料相容性

舊賽事與舊備份沒有飲品欄位時，必須可以正常讀取。

`normalizeTournament()` 應補上：

```js
drinkSettings: {
  enabled: false,
  notice: '',
  changeNotice: '',
  coffeeFlavors: [],
  caffeineFreeOptions: [],
},

participantDetails: {},
```

要求：

- 舊賽事可正常開啟。
- 舊比分不受影響。
- 舊參賽者可正常顯示。
- 舊備份仍可匯入。
- 舊 CSV 仍可輸出。
- 不應要求 D1 資料重建。
- 若 D1 目前保存 tournament JSON，優先沿用既有資料結構，不新增不必要的資料表。

## 16. 測試要求

至少新增或更新以下測試。

### 16.1 報名流程

- 已確認參賽者送出後直接加入 `players`。
- 不需要後台核准。
- `participantStates` 正確建立。
- `participantDetails` 正確建立。
- 名額已滿時拒絕送出。
- 相同選手名稱拒絕重複。
- 正規化後相同電話拒絕重複。
- 關閉填寫後舊 Token 無法使用。

### 16.2 飲品驗證

- 飲品功能開啟時，飲品必填。
- 藍莓不可選加可樂。
- 哈密瓜不可選加可樂。
- 椰子可以選加可樂。
- 停用品項不可被新參賽者選擇。
- 已選過的停用品項仍能在舊資料中顯示。
- 無咖啡因選項可正常保存。
- `displayName` 組合正確。

### 16.3 統計

- 完整飲品名稱正確分組。
- 數量正確。
- `尚未選擇` 數量正確。
- 停用品項的舊選擇仍納入統計。
- 不產生原料分類統計。

### 16.4 報到

- 報到 Checklist 顯示飲品。
- 舊賽事沒有飲品時不報錯。
- 手機版排版不因飲品文字過長而破版。

### 16.5 CSV

- CSV 包含飲品欄位。
- 咖啡完整名稱正確。
- 無咖啡因名稱正確。
- 舊賽事飲品欄位可留空。

### 16.6 回歸測試

不得破壞：

- 瑞士制配對
- 淘汰制
- 四強決賽
- 報到與未報到排序
- 現有賽事備份
- D1 同步
- Sites build

完成後至少執行：

```bash
node tests/registration.test.mjs
node tests/check-in.test.mjs
node scripts/test-fast.mjs
node scripts/test-full.mjs
```

## 18. 驗收條件

功能完成後，以下流程必須成立：
